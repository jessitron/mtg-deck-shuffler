# Decide which verification tests are superfluous

Mountain: overhead
Status: ready-for-human

> _This was generated by AI during triage._

Tickets 02 and 03 make the suite **faster**. This one asks the other question: which of these
tests should exist at all? A test that is redundant, vacuous, or asserting something nothing
depends on costs time on every run forever and gives nothing back.

## Why this can't go to an agent

Deleting a test is a decision about what the Shuffler must never break. An agent can gather the
evidence and make a case; only Jess can say "we don't need to keep proving that."

## Evidence already in hand

**A vacuous assertion, found while implementing 02.** In `verify-library-grouping.spec.ts`, both
flip loops click the flip button and then assert:

```ts
await expect(positionIndicator).toHaveText(`Card ${currentPosition} of ${totalInGroup}`);
```

That is the *same text as before the flip* — which is exactly the property under test
("flipping preserves group-scoped navigation"), but it means **a flip that never happened
passes too.** The test cannot distinguish success from the button doing nothing. It is
currently a comment in the spec pointing here.

Question for this ticket: strengthen it (assert the face actually changed — the back face has a
different card name) or drop it?

**Two near-duplicate flip loops.** `verify-library-grouping.spec.ts` has one for the game page
and one for the prep page, ~60 lines each, differing only in route. Both iterate every card in a
type group looking for a two-faced one. Is the prep/game distinction load-bearing here, or is
one enough?

**Nine query-parameter tests in one file.** `verify-query-parameter-modals.spec.ts` covers
`?openCard`, `?openLibrary`, `?openTable`, `?openHistory`, `?openDebug`, three combinations, and
two "no parameters" baselines — for both game and prep pages. This is the largest spec and one
of the slowest. All nine exercise the same mechanism (`public/modal-query-params.js` reading
`URLSearchParams` and firing an htmx request). Does each parameter need its own end-to-end
browser test, or does the mechanism need one and the parameter table a unit test?

## What would make this decidable

For each spec, three questions:

1. **What would break in front of a player if this test vanished?** If the answer is "nothing we
   couldn't catch elsewhere", it's a candidate.
2. **Is it testing the mechanism or the table?** Nine near-identical cases over one mechanism is
   a parameterization, and parameterizations are cheaper as unit tests.
3. **Has it ever failed for a real reason?** Git history knows. The three table-mode specs that
   were broken for weeks (fixed 2026-08-07) are evidence *for* keeping tests that catch real
   regressions — and evidence about which ones do.

The suite now traces itself (`mtg-fleet-verify`, ticket 01), so "which specs cost the most" is a
query rather than a guess. Cost per spec plus value per spec is the whole decision.

## Sequencing

Do **after 02** — 02 changes the cost side of the ledger substantially, and a test that looked
too expensive at 28s may be fine at 8s. Deciding before then would delete tests for the wrong
reason.

### From the two-faced-cards owner, 2026-08-07

> _This was generated by AI during triage._

Asked whether face state is observable at all, so the vacuous assertion above could be
strengthened rather than argued about. It went and read the code. The answer is specific:

- **Inline surfaces: observable, cleanly.** `.flip-container-outer` gets `.card-flipped` when
  `currentFace === "back"` (`src/view/common/shared-components.ts:104`), server-rendered, true
  the instant the swap settles. This is why `verify-prep-commander-flip.spec.ts` is a sound test
  and the grouping ones aren't.
- **The card modal: not observable.** No class, no attribute, no face-dependent text. A DFC's
  `card.name` is the whole `"Front // Back"` string, so the modal title and `alt` are byte-
  identical on both faces. `views/partials/card-modal.ejs` *receives* `currentFace` and never
  renders it.
- Two indirect observables: `img.modal-card-image`'s `src` (different Scryfall files per face),
  on both pages; and **on prep only**, the flip button's `hx-get=".../?face=<target>"`. The
  **game** modal's flip button is a `hx-post` to a toggling route, byte-identical on both faces
  — useless for assertion.

**So there's a third option beyond strengthen-or-drop, and it's a one-liner:** emit
`data-current-face="<%= currentFace %>"` on `.card-modal-overlay`. The value already reaches the
template unused. That gives the game modal its first real face observable and makes both
grouping loops verifiable. The owner identified it but deliberately didn't do it — it's a code
change, and it belongs to whoever resolves this ticket.

That reframes the question for these two tests: they may not be superfluous so much as
*currently unable to prove their premise*, which is a different and cheaper problem.
