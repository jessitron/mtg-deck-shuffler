# Delete the redundant waits from the verify suite

**Desired behavior:**

### Why this is mostly mechanical

There are 65 `networkidle` sites and 45 `waitForTimeout` sites across 15 spec files. Nearly all
of them are one repeated shape:

```ts
await page.goto(`${BASE_URL}/choose-any-deck`);
await page.waitForLoadState('networkidle');        // ← ~540ms, buys nothing
const preconTiles = page.locator('.precon-tile');
await expect(preconTiles.first()).toBeVisible({ timeout: 10000 });   // already polls
```

`expect(locator)` auto-retries until its timeout, so the wait in front of it is dead time.
`waitForLoadState('networkidle')` is discouraged by Playwright's own docs for exactly this
reason. Every `networkidle` site is followed by one of: another wait, an auto-retrying
`expect`, a locator action (which auto-waits), or a `const x = page.locator(...)` handle whose
very next use is an auto-retrying `expect`.

Classification script used during triage — rerun it to regenerate the site list:
`.scratch/verify-suite-speed/classify-waits.mjs` (run it with the spec directory as argv[2]).

### Verified during triage, not assumed

`verify-query-parameter-modals.spec.ts` (19 `networkidle`, 16 `waitForTimeout` — the heaviest
spec) was swept and re-run:

- **Baseline: 1:15 wall, suite 1.2m, 14 passed.**
- **After removing 33 wait lines: 0:36 wall, suite 32.4s, 13 passed, 1 failed.**

So the win is real and better than 2×, *and* the residue is real. Both numbers are warm-`data.db`
runs back to back; note the condition when you re-measure.

### The one failure is the important part

`prep card modal navigation works - can click through cards` (around line 380) failed. The card
title never changed after clicking next:

```
Expected: not "Captain America, Living Legend"
Received:     "Captain America, Living Legend"
9 × locator resolved to <h3 class="card-modal-title">Captain America, Living Legend</h3>
```

The click genuinely did not advance the card — this is not an assertion that needed longer to
settle, it is behavior that only worked because a sleep preceded it. **Do not paper this back
over with a sleep.** Find out why the click is lost when the page hasn't idled (the modal is
HTMX-swapped in on load; a plausible story is clicking before the swap that binds the nav
handlers has landed, but that is a guess — go look). If it turns out to be a real app race
rather than a test artifact, stop and file it separately rather than absorbing it here.

### The sites that need judgment, not deletion

Everything else is deletable. These are not:

- `verify-query-parameter-modals.spec.ts` ~`:409`, ~`:419` — `waitForTimeout(500)` then a bare
  `.textContent()`. A bare read does not retry, so the sleep is the only synchronization.
  Replace with a real condition on the change (e.g. `await expect(cardTitle).not.toHaveText(before)`),
  and see the failure above — this is that site.
- `verify-mulligan.spec.ts` — two 1800ms waits on a shuffle animation. A real animation is
  running; needs a condition on the animation's end state, or keep the wait and say why.
- `verify-library-grouping.spec.ts` `:257`, `:342` — the `foundFlipCard` loops, where the wait
  sits inside iteration and the loop's own bookkeeping depends on the DOM having settled.

  Don't touch them. Also ticket 03.
- **Resetting `data.db`.** Changes what the suite tests. Not here.
- Changing app code. If the sweep surfaces an app race, file it; don't fix it here.

Both are warm-`data.db` runs an hour apart on the same machine. `Click locator` got *slower*
(5.2s → 7.9s) and that's the change working: those clicks now do their own actionability wait
instead of having a sleep in front of them. `toPass` at 8.2s is what correctness costs.

**A side effect worth more than the speed: the suite stopped varying.** It used to run
9.5 → 5.4 → 5.2 → 3.6 minutes with no changes. Three runs back to back now: 113s, 107s, 107s.
Most of that variance *was* the `networkidle` waits, whose duration depends on whatever the
network happens to be doing.

**The `can click through cards` failure — cause found, and it is not an app race.** The
**animations** owner had it written down already
(`owners/animations/interactions.md:27`, `history.md:112`). The card modal has no animation at
all. Its nav arrows are plain `hx-get` → `hx-target="#card-modal-container"`. A click at
Playwright speed lands its mousedown on a node htmx then replaces, so **no click event fires** —
and `{ force: true }` disables the actionability wait that would otherwise absorb it. The repo
already had the fix in six specs: `expect(async () => { click; assert }).toPass()`. Used that.
**No separate app-race ticket needed.**

**Two negative assertions the mechanical sweep would have silently gutted.** The "no query
parameters" baseline tests assert `toBeEmpty()`, which passes *instantly* whether or not a modal
is about to open — the sleep was the entire test. Caught before running. They don't need a sleep
either: `modal-query-params.js` decides synchronously in its `DOMContentLoaded` handler, and
`page.goto()` resolves on `load`, which is strictly after, so the decision is already made and
cannot change. Each now anchors on a rendered element (`.playmat-game` / `.playmat-prepare`)
first, so it can't pass on a blank page. Reasoning is in the spec, not just here.

**The mulligan sleeps went entirely.** `.library-stack.shuffling` is a real 1.5s animation
(`game.css:332-345`), so 1800ms was honest — but it animates `.library-card-back` transforms,
which none of the asserted locators touch, and the class arrives in the same swap as the state
being asserted. Also learned: **`.shuffling` is never removed**, so a class-based completion
check would be wrong and would pass instantly. Don't invent one. The `Mulligan #2` assertion at
`verify-mulligan.spec.ts:120` is load-bearing — it gates the following Ctrl+Z — and is commented
as such.

**Left undone, deliberately, and filed:**

- **`{ force: true }` is still there** (9 sites). The owner flagged it as the underlying cause.
  Removing it is a second behavioural change and `toPass()` fixes the symptom; one change at a
  time. Now a line in `TODO.md`.
- **A vacuous assertion in `verify-library-grouping.spec.ts`.** Both flip loops assert the
  position indicator reads the same after the flip as before — which is the property under test,
  but means a flip that never happened also passes. Not introduced here. Commented in the spec
  and written up as ticket **04**.

`verify-thrice.sh` was added alongside: three sequential runs with a summary, because one green
run doesn't distinguish "fixed" from "got lucky", and overlapping runs corrupt each other

**Ticket 03 is now the whole story.** `Navigate to "/choose-any-deck"` is 53.9s of a 106.5s run —
**half the suite**, and untouched by this ticket.
