### Why this is mostly mechanical

There are 65 `networkidle` sites and 45 `waitForTimeout` sites across 15 spec files. Nearly all
of them are one repeated shape:

```ts
await page.goto(`${BASE_URL}/choose-any-deck`);
await page.waitForLoadState('networkidle');        // ← ~540ms, buys nothing
const preconTiles = page.locator('.precon-tile');
await expect(preconTiles.first()).toBeVisible({ timeout: 10000 });   // already polls
```

`expect(locator)` auto-retries until its timeout, so the wait in front of it is dead time.
`waitForLoadState('networkidle')` is discouraged by Playwright's own docs for exactly this
reason. Every `networkidle` site is followed by one of: another wait, an auto-retrying
`expect`, a locator action (which auto-waits), or a `const x = page.locator(...)` handle whose
very next use is an auto-retrying `expect`.

Classification script used during triage — rerun it to regenerate the site list:
`.scratch/verify-suite-speed/classify-waits.mjs` (run it with the spec directory as argv[2]).

### Verified during triage, not assumed

`verify-query-parameter-modals.spec.ts` (19 `networkidle`, 16 `waitForTimeout` — the heaviest
spec) was swept and re-run:

- **Baseline: 1:15 wall, suite 1.2m, 14 passed.**
- **After removing 33 wait lines: 0:36 wall, suite 32.4s, 13 passed, 1 failed.**

So the win is real and better than 2×, *and* the residue is real. Both numbers are warm-`data.db`
runs back to back; note the condition when you re-measure.

### The one failure is the important part

`prep card modal navigation works - can click through cards` (around line 380) failed. The card
title never changed after clicking next:

```
Expected: not "Captain America, Living Legend"
Received:     "Captain America, Living Legend"
9 × locator resolved to <h3 class="card-modal-title">Captain America, Living Legend</h3>
```

The click genuinely did not advance the card — this is not an assertion that needed longer to
settle, it is behavior that only worked because a sleep preceded it. **Do not paper this back
over with a sleep.** Find out why the click is lost when the page hasn't idled (the modal is
HTMX-swapped in on load; a plausible story is clicking before the swap that binds the nav
handlers has landed, but that is a guess — go look). If it turns out to be a real app race
rather than a test artifact, stop and file it separately rather than absorbing it here.

### The sites that need judgment, not deletion

Everything else is deletable. These are not:

- `verify-query-parameter-modals.spec.ts` ~`:409`, ~`:419` — `waitForTimeout(500)` then a bare
  `.textContent()`. A bare read does not retry, so the sleep is the only synchronization.
  Replace with a real condition on the change (e.g. `await expect(cardTitle).not.toHaveText(before)`),
  and see the failure above — this is that site.
- `verify-mulligan.spec.ts` — two 1800ms waits on a shuffle animation. A real animation is
  running; needs a condition on the animation's end state, or keep the wait and say why.
- `verify-library-grouping.spec.ts` `:257`, `:342` — the `foundFlipCard` loops, where the wait
  sits inside iteration and the loop's own bookkeeping depends on the DOM having settled.

**Acceptance criteria:**

- [ ] `./verify.sh` passes, all 51 tests, no `.skip`, no widened assertion that stops checking
      what it checked before.
- [ ] Run the full suite **three times in a row** and it passes all three. One green run does
      not distinguish "fixed" from "got lucky" — flakiness is the whole risk of this ticket.
- [ ] Report before/after wall clock **with the cold-or-warm condition stated** (`data.db` is
      never reset; the same tests have gone 9.5 → 3.6 min untouched). Compare like with like.
- [ ] Quote the new `networkidle` / `waitForTimeout` step totals from `mtg-fleet-verify` and
      leave the query link in the ticket comments. Ticket 01 exists so this number is a query.
- [ ] Every wait that survives has a comment saying what it is waiting for and why no assertion
      can express it. A surviving bare `waitForTimeout` with no comment is a bug in this ticket.
- [ ] Say in the comments what happened with the `can click through cards` failure — the cause,
      not just that it's green again.

**Out of scope:**

- **The 42 visits to `/choose-any-deck` (67.0s)** and **the suite's internet dependency**
  (`tls.connect`, 4.5s p95, almost certainly Scryfall). Both are ticket **03** — they need
  decisions from Jess about `workers: 1` and about fixtures.
- **`workers: 1` and `fullyParallel: false`.** Deliberate — "we're testing concurrent state."
  Don't touch them. Also ticket 03.
- **Resetting `data.db`.** Changes what the suite tests. Not here.
- Changing app code. If the sweep surfaces an app race, file it; don't fix it here.
