# Instrument the verify harness so the suite's own time is queryable

Mountain: overhead
Status: ready-for-agent

> _This was generated by AI during triage._

## Agent Brief

**Category:** enhancement

**Summary:** Emit OpenTelemetry spans about the Playwright suite itself — one trace per
verify run, a span per spec and per step — to a new `mtg-fleet-verify` service, so "why is
the suite slow" becomes a query instead of a guess.

**Current behavior:**

`apps/shuffler/verify.sh` runs 51 Playwright tests in 3.6–9.5 minutes. Nothing about the
*suite* is instrumented. A run does emit app spans (the server is started with
`--import ./dist/tracing.js`, and the browser exports too), and those spans have already
answered the only question they can: **it isn't the server.** Across four full runs on
2026-08-07, `SUM(duration_ms)` over all 3,570 app spans in a 6-hour window was ~48 seconds,
against ~22 minutes of suite runs in the same window — so server-side work is ~1–2% of wall
clock, and that 48s is inflated by parent/child double-counting.
Query: https://ui.honeycomb.io/modernity/environments/local/datasets/mtg-deck-shuffler/result/vZWiRDexbsm

The other ~98% is Playwright startup, browser launch, process spawn, navigation, and 44
fixed `page.waitForTimeout` sleeps (~39 seconds of floor, before the readiness polls). None
of it is measured. The suite also has no single duration: four consecutive runs of the same
tests with no changes went 9.5 → 5.4 → 5.2 → 3.6 minutes, and `data.db` is never reset
between runs.

**Desired behavior:**

A verify run produces one trace, rooted at a `verify run` span, with a child span per spec
file, per test, and per Playwright step — including each `page.goto` and each explicit wait.
Every span carries a run id and enough condition attributes that two runs can be compared
honestly. Spans go to service `mtg-fleet-verify` (chosen deliberately ship-neutral, so the
Tabletop's and Spine's suites can join the same dataset later — put the ship on a span
attribute, not in the service name).

**Key interfaces:**

- **A custom Playwright reporter** is the only emitter. Playwright's `Reporter` hooks
  (`onBegin`, `onTestBegin`, `onTestEnd`, `onStepEnd`, `onEnd`) carry `result.startTime`,
  `result.duration`, and the full step tree — which already includes navigations and each
  `waitForTimeout`. Build spans from those timestamps in the reporter process. With
  `workers: 1` this means one process, one tracer provider, one flush, and no per-worker
  provider lifecycle. Only add in-test spans if the step tree proves insufficient — and if it
  does, say why in the ticket rather than adding them silently.
- **The reporter's own small tracer provider** — a basic provider with a batch span processor
  over the OTLP HTTP trace exporter, `service.name` set **in code on the resource** (not from
  env), no auto-instrumentation, no sampler.
- **A span processor that stamps the run id on every span**, so no call site has to remember.
  Imitate the Tabletop browser wrapper's `GlobalAttributesSpanProcessor`.
- **Root-span attributes**, at minimum: the run id; whether the run was cold or warm
  (`data.db` presence and/or row count); the short git SHA; and the ship the suite belongs to.
- **`verify.sh`** gains the service-name override on the `npx playwright test` invocation and
  the reporter wiring. Its `.be`-then-`.env` sourcing order must not move.

**Three non-negotiables** — from the `fleet-is-observable` owner, consulted during triage.
Each is a silent failure, so none is optional:

1. **Set `OTEL_SERVICE_NAME` per-invocation on the `npx playwright test` command only.**
   `.env` exports it and the app server inherits it. Exporting a new value in `verify.sh`
   after sourcing `.env` renames the **server** too — its spans move to the new dataset and
   the app-vs-harness measurement above silently evaporates. Follow the shape of the existing
   `PORT=$VERIFY_PORT node ...` and `TABLETOP_URL` overrides, and leave a comment saying why,
   because nothing about the failure is visible. Also check the tabletop-integration spec,
   which spawns a second server from inside a spec and inherits the runner's env.
2. **Do not reuse the app's `src/tracing.ts`.** It is import-for-side-effect with no export
   and no flush handle, it registers the ESM hook and loads full auto-instrumentation (which
   would trace the test runner's own fs/http/child_process — noise on top of the signal), and
   it takes `service.name` from the ambient env. Write a small dedicated provider instead.
   (For the record: `BackgroundChatterSampler` would *not* have dropped harness spans — it
   returns false with no `http.target`/`url.path` — so this is about noise and lifecycle, not
   sampling.)
3. **Do not inject `traceparent` into the browser** (`page.setExtraHTTPHeaders`,
   `context.route`) without going back to `fleet-is-observable-review` first. The app's
   sampler is `ParentBasedSampler({ root: BackgroundChatterSampler })`: a sampled remote
   parent means `ParentBased` honors it and never consults the root sampler, so every static
   asset and health hit during 51 tests gets traced at 100%. That re-creates exactly the
   volume problem commit `0f42c95` was written to fix, and it will look like success — lots of
   lovely connected traces — while it happens. If harness→app correlation is wanted, **stamp,
   don't parent**: pass the run id as a header the Shuffler stamps onto its spans as an
   attribute, or join on run id + time across datasets.

**Flush:** `onEnd` must `await` a bounded `shutdown()` (which flushes) before the process
exits, or the last batch is lost. Give it a timeout, and make it **never fatal** — a
telemetry problem must not read as a test failure. Same posture as `deploy-marker.sh`'s
`|| true`.

**Acceptance criteria:**

- [ ] `./verify.sh` produces spans in Honeycomb team `modernity`, env `local`, dataset
      `mtg-fleet-verify`.
- [ ] One run is one trace: a single root span with spec, test, and step spans beneath it.
- [ ] `page.goto` calls and `waitForTimeout` waits appear as their own spans with durations.
- [ ] Every span in a run carries the same run id attribute.
- [ ] The root span carries the run id, a cold-vs-warm indicator, the git short SHA, and the
      ship name.
- [ ] Spans for the *app* still land in `mtg-deck-shuffler` / `mtg-deck-shuffler-web` —
      verify explicitly that the app's service name did not change (this is non-negotiable #1;
      assert it, don't assume it).
- [ ] No new spans appear in the app datasets as a result of harness instrumentation
      (i.e. non-negotiable #3 held): compare app-dataset span count per run before and after.
- [ ] Killing the exporter (bad key, unreachable endpoint) fails the run's telemetry silently
      and does **not** fail the suite or change its exit code.
- [ ] A query over `mtg-fleet-verify` can answer: which specs are slowest, and how much of a
      run is fixed sleeps. Leave the query links in the ticket comments.
- [ ] After landing, call `fleet-is-observable-update` — this is the fleet's **first**
      dev-tooling instrumentation, so the pattern becomes the runbook, and
      `notes/add-opentelemetry.md` should point at it.

**Out of scope:**

- **Optimizing the suite.** That's ticket 02, and it is deliberately not specified yet: the
  whole point of this ticket is to get the data first. Do not delete a `waitForTimeout`, do
  not touch `workers: 1` / `fullyParallel: false` (both deliberate — "we're testing concurrent
  state"), do not reset `data.db`. Measure only.
- **The two known app-side costs.** `tls.connect` (4 spans, 4.5s p95 — the suite still reaches
  the internet, almost certainly Scryfall) and `GET /proxy-image` (4 calls, 2.4s total) are
  real but are the ~1–2%, and they're recorded in ticket 02.
- **The app's missing SIGTERM flush** and **the dead `TEST_EXIT_CODE` branch** in `verify.sh`
  — both found during triage, both filed separately in `TODO.md`. Don't let them expand this.
- Instrumenting the Tabletop's or Spine's suites. The service name leaves room for it; doing
  it is separate work.
