# The suite runs against a shared 37 MB data.db that is never reset

Mountain: overhead
Status: claimed
Type: grilling

> _This was generated by AI while charting `../map.md`._

## Question

`verify.sh` starts the server with default env, which means SQLite against `./data.db` — the
same file the developer's own `./run` uses. It **never resets it**. Telemetry says the file is
now **37 MB and grows ~1 MB per verify run** (32.4 → 36.5 MB over the runs recorded).

**Should a verify run get a fresh database?**

## Why this is takeable now

Nothing blocks it. It's independent of the setup shape (03) and it's an *input* to the
parallelism decision (06), not an output — 06's second claim, "single worker for state
isolation", is really a question about this file.

## The two things this decides

### 1. Determinism

Every verify run starts from whatever the last run, and the developer's manual poking, left
behind. Tests that pass today can fail tomorrow because of accumulated state, and there is no
way to reproduce a failure from a clean slate. That's a correctness property, and it's arguably
more valuable than the speed.

It also means **the suite is not currently reproducible across Jess's computers** — different
machines have different `data.db` contents.

### 2. The cold-start number nobody has

`verify.sh` records `verify.data_db.existed` and `verify.data_db.bytes` precisely so this could
be asked. The answer: **all 13 runs in telemetry are warm.** There is no cold run in the data at
all — the delta is absent, not unqueried.

The `verify.sh` comments record four early runs going **9.5 → 5.4 → 5.2 → 3.6 minutes**, which
looks like warming, but that period overlaps the sleep-removal work of ticket 02, so it is
confounded and proves nothing. Somebody needs to move `data.db` aside and run the suite once.

**This matters to the destination.** If a cold suite is 3 minutes and a warm one is 60 seconds,
then "an agent can run the full suite without waiting minutes" is only true for agents on a
machine that has already run it — which is not most agents, and not CI.

## Options

- **Fresh SQLite file per run.** `SQLITE_DB_PATH` already exists (`src/server.ts:24, 37, 51`);
  `verify.sh` could point it at a temp file and delete it on the existing `trap cleanup EXIT`.
  Small change, full isolation, and it makes the cold-start cost the *only* cost — which may be
  the thing that makes 60s unreachable, so measure before committing.
- **In-memory adapters.** `PORT_PERSIST_STATE=in-memory`, `PORT_PERSIST_PREP=in-memory`,
  `PORT_CARD_REPOSITORY=in-memory` are already wired (`src/server.ts:18-53`). Fastest option.
  But the card repository holds hydrated card definitions, so an empty one may mean the suite
  can't render a deck at all without seeding — check before assuming.
- **Keep the shared file, but reset it.** Delete and let the server recreate. Cold every run,
  honest numbers, no isolation subtleties.
- **Leave it.** Accept warm-only runs and non-reproducibility as the price of speed. Defensible
  if the cold cost turns out to be minutes — but then say so out loud on the map, because it
  contradicts the destination's third clause.

## First step, whatever we choose

Move `data.db` aside and run `./verify.sh` once. That single measurement decides most of this
ticket, and it costs one run. **Do it before arguing about the options.**

## Comments

### Cold-start measurement, 2026-08-07

Did the "first step": moved `data.db` aside (39,141,376 bytes) and ran `./verify.sh` once
against a server that recreated it from scratch — i.e. `verify.data_db.existed` would read
`false` for this run.

**Result: 49 passed (52.0s), 57.2s wall total.** That's not "minutes" — it's roughly in line
with (if not faster than) the 50.2s warm baseline the map records post-ticket-04. Restored
`data.db` immediately afterward (same file `./run` uses).

**This changes the ticket's premise.** The map worried cold start might be the thing that makes
60s unreachable. It isn't — at least not at 37 MB. So determinism/reproducibility (the other
half of this ticket) is the real remaining question, independent of any speed concern.
