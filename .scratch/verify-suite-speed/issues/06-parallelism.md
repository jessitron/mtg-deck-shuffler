# Should the verify suite run in parallel?

Mountain: overhead
Status: resolved
Type: grilling
Blocked by: 03 (resolved — unblocked)
Map: ../map.md

> _This was generated by AI while charting `../map.md`._
> Split out of `03-setup-cost-and-isolation.md` (decision 3) while charting the map.

## Question

`playwright.config.ts` pins `workers: 1` (`:16`, "Single worker for state isolation") and
`fullyParallel: false` (`:13`, "we're testing concurrent state").

Telemetry confirms this is real, not nominal: the 16 `spec:` spans sum to **99.0s** and the
root `verify run` span is **104.1s**. The specs run strictly serially, so **the entire suite is
one core's worth of work**. On any modern laptop that is the largest untapped multiple
available — and the one most likely to make the suite flaky.

**Do we raise `workers`, and what has to be true first?**

## Why this is blocked by 03

Shared setup and parallel workers pull in opposite directions, and 03 decides the setup shape.

- If 03 picks **API-seeded, per-test games**, each test owns its own game id and the specs
  become genuinely independent — parallelism gets much safer, possibly free.
- If 03 picks **one shared game reused across tests**, parallelism gets *harder*, because the
  shared mutable state is exactly what workers would race on.

Deciding parallelism before 03 means deciding it twice.

## What the comments are actually protecting

Two different claims are load-bearing here, and they should be separated before anything
changes:

1. **"We're testing concurrent state."** Is there a spec that genuinely exercises two
   simultaneous actors against one game? If so, it needs serialisation — but it can be pinned
   with `test.describe.serial()` rather than forcing the whole suite to one worker. Find it or
   disprove it.
2. **"Single worker for state isolation."** All specs share one server, one 37 MB `data.db`,
   and — for the ones that use it — one game. Isolation today is *incidental*, achieved by
   never running two things at once. That's ticket 07's territory, and 07 is not blocked, so
   its answer should be in hand before this is decided.

## Constraints already known

- `verify-tabletop-integration.spec.ts:37` spawns **its own Tabletop server** in `beforeAll` on
  a random port. It is the only spec with `beforeAll`/`afterAll` and the only one with a
  120s timeout. It may need pinning to its own project or serial block.
- `verify.sh` picks one random `VERIFY_PORT` and starts **one** server for the whole run.
  Parallel workers would share it — which is fine for HTTP, and the question is entirely about
  the database and game state behind it.
- `retries: 0`. Any flakiness introduced here shows up as a hard failure, which is the right
  default but means the bar for "safe" is high.

## How to decide it honestly

Don't reason about it — measure. Raise `workers`, run the suite ten times, and query
`mtg-fleet-verify` for the pass rate and the duration spread. A parallel suite that is 3× faster
and fails 1 run in 10 is **worse than the serial one**, because a suite an agent can't trust is
a suite an agent re-runs. The destination says "an agent can run the full suite" — trust is part
of that, not a bonus.

## Answer

**Raise `workers` to 4. `fullyParallel` stays `false`** (untested — a further lever, not needed
to hit the destination).

Both load-bearing claims resolved false, once separated:

1. **"We're testing concurrent state."** No spec exercises two actors mutating one game
   concurrently. `verify-tabletop-integration.spec.ts` opens a second page (`context.newPage()`)
   as a **read-only spectator** watching the same page's actions over the websocket — one
   actor, one observer, not two writers. Nothing needs `test.describe.serial()`.
2. **"Single worker for state isolation."** Ticket 03 already made this moot: every spec but
   one seeds its own game via `POST /deck` + `POST /start-game` (`seedGame.ts`), so specs own
   disjoint game ids. The one shared resource is the single `better-sqlite3` connection inside
   the one server process `verify.sh` starts — but that connection is synchronous and lives in
   one Node event loop, so concurrent HTTP requests from parallel workers just queue on it
   in-process; there's no multi-process file-lock contention to worry about. Isolation was never
   about worker count.

**Measured, not reasoned:** `workers: 4`, ten consecutive `./verify.sh` runs, no other change.

| | |
| --- | --- |
| Pass rate | **10/10**, 48 passed + 1 skipped (Tabletop unbuilt) every run — no failures, no retries |
| Test duration | 12.7s – 14.7s (was 99.0s serial) |
| Whole `verify.sh` | 16.9s – 18.8s (was 104.1s serial) — **~5.7× faster**, tight spread |

`verify-tabletop-integration.spec.ts`'s own `beforeAll`-spawned Tabletop server and 120s timeout
caused no issue — it's the only file doing that, so no port collision is possible regardless of
worker count.

This blows past the destination's third clause (60s) on its own. Left as fog: whether
`fullyParallel: true` (parallelizing tests *within* a file too) is worth measuring — no spec
needs it to hit 60s, and claim 1 above suggests it'd be safe, but it's untested.
