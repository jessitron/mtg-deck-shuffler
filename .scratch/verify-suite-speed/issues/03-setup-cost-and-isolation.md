## Why this can't go to an agent

Three decisions here are Jess's, not an agent's. Each one trades away something the suite
currently has, and none of them has an obviously right answer.

## Decision 1 — the 42 visits to `/choose-any-deck` (67.0s)

Ticket 01 measured **42 navigations to one page**, 67.0s in total (partly overlapping the
`networkidle` waits ticket 02 removes — re-measure after 02 lands before deciding anything).

Nearly every spec opens with the same `setupGame` / `setupPrep` helper: go to
`/choose-any-deck`, click the first precon tile, wait for `/prepare/*`, click Shuffle Up, wait
for `/game/*`. Written out longhand in each spec file rather than shared.

The question is whether that setup can be paid once instead of 42 times. The ways to do it all
cost something:

- **A Playwright fixture or `beforeAll` that creates one game and shares it** — the tests then
  share mutable state, which is the thing `workers: 1` / `fullyParallel: false` was chosen to
  make safe. Sharing setup across tests is a different bet than running them in order.
- **Seed the game directly through the API or the DB**, skipping the UI clicks — fast, but the
  click-through path stops being exercised by every spec. That may be fine (one spec could own
  it) or may be exactly the coverage that caught things.
- **`storageState` / reuse the browser context** — helps with the browser, not with the game
  creation.

**The real question for Jess:** is the precon→prepare→game click-through something every spec
should re-prove, or is it one spec's job with everything else seeded?

## Decision 2 — the suite reaches the live internet

**Split out to ticket 11** — kept here for the original framing/history; see that ticket for
the settled design.

`tls.connect` — 4 spans, **4.5s p95** — means a verify run talks to the internet, almost
certainly Scryfall. `GET /proxy-image` (4 calls, 2.4s) is the slowest route per call.

Small in total time. But it means the suite can fail because Scryfall is slow, rate-limits, or
is down, and it means the suite can't run offline. That's a reliability and CI question more
than a speed one — worth ~7s and a dependency.

Options: a fake `CardImagesPort` for the run (the port and `FakeCardImagesGateway` already
exist), route-level interception in Playwright, or leave it and accept the coupling.

Note `test/verification/verify-proxy-image.sh` deliberately hits the live CDN and should
probably stay that way — it exists to catch Scryfall's Cloudflare front end returning 400 to
Node's default User-Agent. Whatever gets faked, that check needs to keep being real somewhere.

## Decision 3 — parallelism

`workers: 1` and `fullyParallel: false`, with the comment "we're testing concurrent state."
Raising workers is the single biggest lever available and also the one most likely to make the
suite flaky. It interacts with decision 1: shared setup and parallel workers pull in opposite
directions.

Not a free win. Explicitly Jess's call.

## Sequencing

**Do ticket 02 first and re-measure.** 02 removes the `networkidle` waits that are folded into
the 67.0s navigation figure, so the setup cost will look different — possibly much smaller —
afterward. Deciding decision 1 against today's number risks solving a problem 02 already shrank.

### Charting the map, 2026-08-07

> _This was generated by AI while charting `../map.md`._

**Decisions 1 and 2 are the same problem.** Measured on run `96588aeb`:

- `GET /choose-any-deck` costs **26.6 ms** server-side (avg over 41 calls, p95 32 ms).
- The navigation step costs **1,306 ms**. So ~1,280 ms of it is the browser waiting for `load`.
- `views/partials/deck-selection-precon.ejs:17` emits **191 remote `<img>` to Scryfall
  `art_crop`** — one per precon deck — plus per-colour SVGs at `:26`.

The 42 trips are slow *because of* the live internet dependency. Decision 2's "4 spans, 4.5s"
counted only server-side `tls.connect`; the browser's 191-images-per-navigation never appear in
server telemetry. The real figure is 42 × 191 image requests.

**This kills the framing that decision 1 is about coverage.** The question is no longer "should
every spec re-prove the click-through path" as an abstract trade — it's that the click-through
path costs 1.3s *only because the deck chooser is image-heavy*, and there are now three
distinct ways out:

1. **Seed through the API, no navigation at all.** `POST /deck` (form-encoded
   `deck-source=precon&precon-deck=<filename>`) → 302 `Location: /prepare/N`; `POST /start-game`
   (`prep-id=N`) → 302 `Location: /game/M`. Both are plain form posts, both work over
   `page.request.post()` with `maxRedirects: 0`. Zero `/choose-any-deck` visits, and the
   click-through stays proven by `verify-precon-to-prepare.spec.ts`, which exists for exactly
   that. Confirmed present at `src/app.ts:337` and `src/app.ts:458`.
2. **Make the deck chooser cheap** (lazy-load images) so 42 navigations stop hurting. That's
   ticket 05, and it's blocked on this one — if we pick option 1, the test benefit vanishes.
3. **`POST /restart-game`** (`src/app.ts:604`) reuses a persisted prep, so one prep-create can
   seed N games.

**A fact worth chasing during this ticket:** three of the 42 navigations take **84–90 ms**, not
1,300 — all three in `verify-developer-mode.spec.ts`. Nobody knows why. Whatever those three do
differently may be the cheap fix for the other 39.

**Also:** there is no shared setup helper. `setupGame`/`setupPrep` is copy-pasted longhand into
nine spec files with drifting names and selectors (`verify-library-grouping.spec.ts:35` submits
the form via `page.evaluate`, unlike every other copy). Whatever this ticket decides, it should
land as **one** helper — the duplication is why the decision has to be made once and applied 42
times.

**Decision 3 (parallelism) has moved to ticket 06**, which is blocked by this one. The two pull
in opposite directions and shouldn't be decided in the same breath.

### Grilled with Jess, 2026-08-07 — decision 1 settled, decision 2 split out

> _This was generated by AI, recording a `/grilling` session._

**Decision 1 — seed, don't navigate.** One shared helper (`seedGame()` or similar) that every
spec but one calls: `POST /deck` (form-encoded `deck-source=precon&precon-deck=<filename>`) →
`POST /start-game`. Zero `/choose-any-deck` navigations in 41 of 42 specs.
`verify-precon-to-prepare.spec.ts` keeps driving the real click-through — it's the one spec
whose job is proving that path still works. The helper always mints a **fresh** game; no
sharing across tests, even for read-only specs, so parallelism (ticket 06) stays a live option
later rather than being foreclosed for a few seconds of setup time.

**Ticket 05 ruled out of scope for this map.** With 41 of 42 navigations gone, the deck
chooser's 191 images stop costing the suite anything worth a ticket. Real product concern,
just not a test-speed one — moving to `TODO.md`.

**Decision 2 split out to ticket 11.** Mid-grill it became clear the internet dependency isn't
the deck chooser at all — it's every visible card's `<img src>` pointing straight at
`cards.scryfall.io` (see ticket 11 for the full finding and design). Jess: "these are two
distinct changes that absolutely should not be implemented in the same session... the proxy
change is a deep conceptual change in the app, and should totally be its own ticket." Right
call — decision 1 is a test-only change; decision 2 changes how every card image is served,
for every real player, not just the suite.

### Landed, 2026-08-07

`test/verification/seedGame.ts` — `seedPrep()`/`startGame()`/`seedGame()`, all built on
`page.request.post()` against `/deck` and `/start-game` so cookies land in the same browser
context the test goes on to interact with. `getPreconDisplayName()` mirrors
`LocalFileAdapter`'s title cleanup for the one spec (`verify-deck-title-placement.spec.ts`)
that asserts on the deck title text without a tile to read it off first.

Every spec but `verify-precon-to-prepare.spec.ts` converted — including
`verify-library-command-zone-swap.spec.ts`, not listed above but found with the same
`setupGame`/`selectDeck` shape during the sweep. Table-mode specs pass `table-name`/
`player-name` straight to `POST /start-game` (the route reads `req.body` either way) instead
of filling and submitting the real disclosure form — `verify-table-mode.spec.ts`'s first test
still opens the disclosure to assert the inputs render, since that's a real assertion about
the prepare page, not test setup.

**Full suite: 106.5s → ~55s**, under the map's 60s destination — though ticket 04
(superfluous tests), 06 (parallelism), and 11 (image proxy) aren't landed yet, so this alone
doesn't close the map.

**Found in the process, not part of decision 1:** seeding through the API skips whatever
settle time the real click-through happened to absorb, which uncovered a pre-existing race in
the Ctrl+Z undo hotkey — `game.js`'s keydown handler clicks a `.undo-button` that's swapped in
out-of-band, the same click-straddles-settle class of flake `owners/animations/interactions.md`
already documents for direct clicks, just via keyboard. Two specs
(`verify-mulligan.spec.ts`, `verify-game-menu.spec.ts`) got the same `toPass()` retry pattern
already used elsewhere in the suite. Confirmed by running the *original* click-through suite
twice back-to-back (both clean) against the seeded suite three times (2 of 3 flaked before the
retry fix, 0 of 5 after) — the race was always there, seeding just stopped masking it.
