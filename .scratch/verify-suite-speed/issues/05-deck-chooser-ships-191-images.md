# The deck chooser ships 191 remote Scryfall images on every visit

## Question

`/choose-any-deck` renders a tile per precon deck — **191 of them**, each with a remote
`<img src>` pointing at Scryfall's `art_crop` CDN
(`views/partials/deck-selection-precon.ejs:17`), plus per-colour SVGs (`:26`). Nothing is
lazy-loaded, paginated, or virtualised.

Measured cost: the server renders in **26.6 ms**, and the browser then spends **~1,280 ms**
waiting for `load`. Across the suite's 42 navigations that is **54.9 seconds — 52.7% of the
run**.

**Should the page stop doing this?**

## Why this is blocked by 03

If ticket 03 chooses API-seeded setup, the suite stops visiting this page 42 times and the
55 seconds evaporates without touching the app. This ticket's test-side justification vanishes
with it, and what's left is a pure product question — which the map rules **out of scope**
(see `../map.md` § Out of scope): it would leave here for `TODO.md`.

So resolve 03 first. This ticket only stays on the map if 03 decides the suite should keep
navigating to the deck chooser.

## What's already known

- **The 84–90 ms outlier.** Three of the 42 navigations — all in
  `verify-developer-mode.spec.ts` — complete in 84–90 ms instead of ~1,300. Whatever those do
  differently is the strongest available lead, and understanding it is probably the first
  thing this ticket should do. It may be a dev-mode branch that skips the tile list entirely.
- The tile list is not rendered by `/choose-any-deck` itself. The page is a shell; the tiles
  arrive via `hx-get="/deck-selection-tabs/precon"` with `hx-trigger="load"`
  (`src/app.ts:315`). So there are two requests, and the images belong to the second.
- **A separate, unrelated waste worth fixing regardless:** `GET /choose-any-deck`
  (`src/app.ts:303`) calls `deckRetriever.listAvailableDecks()` and passes the result to a
  template that **never reads `availableDecks`**. `LocalFileAdapter.listAvailableDecks()`
  (`src/port-deck-retrieval/localFileAdapter/LocalFileAdapter.ts:12-60`) synchronously reads
  and `JSON.parse`s all 191 deck files — ~15 MB — with no caching, and it happens twice per
  navigation (again at `src/app.ts:317`, where it *is* used). The measured 26.6 ms says the OS
  page cache is absorbing this, so it is **not** the bottleneck — but deleting a dead 15 MB
  parse is free and shouldn't wait for a decision.

## Options, if it survives 03

- `loading="lazy"` on the tile images — one attribute, browser handles the rest.
- Paginate or virtualise the tile list; 191 decks is a lot of tiles for a human too.
- Serve the art from the Shuffler (the existing `/proxy-image` route, cached) rather than
  191 cross-origin connections.
- Leave it. A real player visits this page once, not 42 times.

## Owners to consult

`shuffler-looks-like-itself` — this changes what a player sees on the deck chooser, and lazy
loading or pagination is a visible design change, not just a perf one.
