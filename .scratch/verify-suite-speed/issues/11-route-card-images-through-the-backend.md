# Route card images through the backend instead of straight to Scryfall

Mountain: overhead
Status: claimed
Map: ../map.md

> _This was generated by AI, split out of ticket 03 after a `/grilling` session, 2026-08-07._

## Why this is its own ticket

Split out of ticket 03 mid-grill. Decision 1 there (seeding games instead of navigating) is a
test-only change. This one changes how every card image is served, for every real player, not
just the verify suite — a deep conceptual change in the app, per Jess, and shouldn't land in
the same session or commit as the test-only work.

## Current behavior

Every visible card face renders as a real `<img>` pointing straight at Scryfall's CDN:

- `getCardImageUrl()` (`src/types.ts:69`) returns the card's stored `imageUris`/`backImageUris`
  (baked into deck JSON at ingestion time) or, as a fallback, constructs a bare
  `https://cards.scryfall.io/...` URL.
- `shared-components.ts` (lines 87–170) uses that URL directly as `<img src>` for hand,
  battlefield, and two-faced card renders. Only the card-back (`CARD_BACK`,
  `/images/mtg-card-back.jpg`) and library stack are local assets.
- This is independent of `CardImagesPort`/`ScryfallCardImagesGateway` — that port is used
  exactly once, at deck-ingestion time (`server.ts:58`, plus the MTGJSON/backfill/download
  scripts), to enrich a `CardDefinition` with the URLs it will later render. It has nothing to
  do with what the browser fetches at render time.
- `/proxy-image` (`src/app.ts:1698`) already exists but is used for exactly one thing:
  `copyCardToClipboard` in `public/game.js:83`, fetching the image server-side so it can be
  written to the clipboard as a blob. It sets CORS and `Content-Type` but no `Cache-Control`,
  `ETag`, or `Last-Modified` — no caching signal today.

Consequence for the verify suite: every spec that reveals a hand or battlefield card makes a
real request to `cards.scryfall.io`, regardless of how the game was created — ticket 03's
seeding change does not touch this.

## Desired behavior

Generalize `/proxy-image` to be the `src` for every rendered card image, not just the
clipboard-copy path — so the browser always talks to our backend, never directly to Scryfall.

- **The gateway defines size/format.** Move the size/format decision (currently a bare
  `ImageFormat` parameter threaded through `getCardImageUrl()`) into the gateway; the
  `ScryfallAdapter` resolves the likely Scryfall URL for whatever size/format the gateway asks
  for, rather than `shared-components.ts` constructing it inline.
- **Cache-Control on the route.** Scryfall's card image URLs are content-addressed
  (versioned) — a given cardId+face+size+format is permanently the same bytes. Add
  `Cache-Control: public, max-age=<long>, immutable` (or similar) to the route's response, so
  the browser caches through our domain exactly as it would have through Scryfall's — this is
  the piece that keeps "browser caches instead of hitting our server on every reload" true.
  No server-side caching yet; that's a "someday" improvement this shape enables but does not
  require (see Out of scope).
- **A fake for verify runs.** Wire a fake image-serving implementation into the route for the
  suite, so it never touches live Scryfall for card art. `verify-proxy-image.sh` stays the one
  place deliberately hitting the live CDN (it exists to catch Scryfall's Cloudflare front end
  returning 400 to Node's default User-Agent — see `notes/AGENT-NOTES.md`). Existing
  `FakeCardImagesGateway` (`src/port-card-images/FakeCardImagesGateway.ts`) is the wrong shape
  for this — it fakes ingestion-time URL enrichment, not image bytes at serve time — so this
  needs a new fake that serves actual image bytes (a small local placeholder), not just a URL.

## Acceptance criteria

- [ ] Every card `<img>` in the game/prepare views (`shared-components.ts`) points at our
      backend route, not `cards.scryfall.io` directly.
- [ ] The route sets cache headers such that a repeat request for the same card+face+size+format
      is served from the browser cache, not re-fetched.
- [ ] The verify suite makes zero requests to `cards.scryfall.io` for card rendering (confirm via
      harness telemetry or a Playwright network assertion), aside from
      `verify-proxy-image.sh`, which is deliberately exempt.
- [ ] `copyCardToClipboard` still works unchanged — it can keep using the same route.
- [ ] No behavior change for real players beyond "images come from our domain" — same images,
      same sizes, same visual result.

## Out of scope

- **Server-side caching of fetched images.** This change makes it possible ("someday"), and
  moves the ingestion-time image cost from Scryfall's CDN onto our own outbound requests, but
  actually caching (disk, CDN, or otherwise) is a separate, sizeable piece of work — don't fold
  it in here.
- **Changing what size/format we currently render at.** The gateway gets to *define* size/format
  going forward; this ticket doesn't need to change today's choices.
